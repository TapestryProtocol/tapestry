# A10.43 Decide how firmware ships as a published Tapestry that a new instance installs by import, so firmware leaves the repo

A decision task under Loom's A10 (Graph operations), drafted from proposal P-160. This is its plan. The decision is ADR [graph-operations-first-slice/0043](../../engineering-team/decisions/graph-operations-first-slice/0043-firmware-ships-as-pinned-tapestry-releases.md), in the same pull request. Its decider accepts it by merging it.

## The question

The firmware is the JSON under `firmware/` (BIBLE §7). `firmware/active` points at `versions/v1.0.0`, which defines 41 concepts and 11 relationship types, with their elements and sets. Every instance's install reads those files, and the instance's own assistant signs each concept's letters. So a firmware concept's address is `39998:<that instance's assistant>:<slug>`, and code builds it that way throughout (`firmware.conceptUuid`).

David wants the firmware published as a Tapestry, a graph of concept graphs (BIBLE §6), that a new instance installs with an import, so the firmware no longer has to live in the repo. A10's operations cover the pieces: export nostr (A10.34) publishes a scope, import nostr (A10.32) records letters as nodes, copy-node (A10.24) makes a node of your own from someone else's, and seed-firmware (A10.37) installs. Nothing yet says how they fit together for firmware.

## What the decision settles

1. Whose addresses an instance uses for its firmware: its own, with a record of where each node came from, or the publisher's.
2. Who signs the published firmware.
3. Which release an instance installs, and who chooses it.
4. How a release is named, pinned and checked, so that a pinned release can still be fetched after the next one is published.
5. How an update keeps local edits (A10.37), and where ADR 0041's graph-rule items differ.
6. What stays in the repo once the firmware leaves it, and the check that has to pass before it goes.
7. What each A10 task then has to do, and the stories that follow.

The ADR weighs four ways to ship the firmware: a release installed as the instance's own nodes, a release used at the publisher's addresses, a file bundle with no nostr, and keeping `firmware/` with A10.37 built on its files.

## Who needs it

- **Seed-firmware (A10.37),** whose source changes from `firmware/active/` to a published release.
- **Export nostr (A10.34),** which makes the releases.
- **Import nostr (A10.32) and copy-node (A10.24),** whose relay reading and link back seed-firmware shares.
- **Whoever starts a new instance,** which would install its firmware from relays rather than from the image's files.
- **Whoever keeps the firmware,** whose changes would stop being pull requests to `firmware/` and become releases.

## Done when

The decider has merged the ADR. It names whose addresses instances use, who signs, how a release is chosen, pinned and checked, what stays in the repo and the check before `firmware/` goes, and the stories that follow, with what each changes.

## Not in this task

- **The builds.** Each follow-on story is a task of its own once the ADR is merged. This pull request changes no code and no firmware.
- **The exact wire format of a release.** The ADR fixes its outline: the release element's d-tag names its version, its members' d-tags name the release, and it lists its members by address and id. The exact form is the release convention's, drafted in this repo's `protocols/drafts/` first, and is a record task of its own.
- **Moving existing instances' graphs.** The recommended option keeps every instance's addresses as they are, so nothing moves. Using the publisher's addresses would need a migration task of its own.
- **Export's open questions that firmware doesn't need answered:** whether an export carries other people's elements (question 9 in §10 of the catalog, [docs/GRAPH_OPERATIONS_CATALOG.md](../GRAPH_OPERATIONS_CATALOG.md)), references to nodes with no nostr address (question 4 in §5 of the design doc, [docs/GRAPH_OPERATIONS_DESIGN_HANDOFF.md](../GRAPH_OPERATIONS_DESIGN_HANDOFF.md)), and who may sign as the assistant (the catalog's question 2). They stay with A10.34.
