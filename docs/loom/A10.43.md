# A10.43 Decide how firmware ships as a published Tapestry that a new instance installs by import, so firmware leaves the repo

A decision task under Loom's A10 (Graph operations), drafted from proposal P-160. This is its plan. The decision is ADR [graph-operations-first-slice/0043](../../engineering-team/decisions/graph-operations-first-slice/0043-firmware-ships-as-pinned-tapestry-releases.md), in the same pull request. Its decider accepts it by merging it.

## The question

The firmware is the JSON under `firmware/` (BIBLE §7). `firmware/active` points at `versions/v1.0.0`, which defines 41 concepts and 11 relationship types, with their elements and sets. Every instance's install reads those files, and the instance's own assistant signs each concept's letters. So a firmware concept's address is `39998:<that instance's assistant>:<slug>`, and code builds it that way throughout (`firmware.conceptUuid`).

David wants the firmware published as a Tapestry, a graph of concept graphs (BIBLE §6), that a new instance installs with an import, so the firmware no longer has to live in the repo. A10's operations cover the pieces: export nostr (A10.34) publishes a scope, import nostr (A10.32) records letters as nodes, copy-node (A10.24) makes a node of your own from someone else's, and seed-firmware (A10.37) installs. Nothing yet says how they fit together for firmware.

## What the decision settles

1. Who signs the published firmware.
2. Whose addresses an instance uses for its firmware: its own, each node linked back to the letter it came from, or the publisher's.
3. How a release is named and pinned, so that a pinned release can still be fetched after the next one is published, and how an update lands without undoing local edits (A10.37).
4. What stays in the repo once the firmware leaves it.
5. What each A10 task then has to do, and the stories that follow.

The ADR weighs three options for the second question, which shapes the rest: install and adopt, the publisher's addresses everywhere, and a file bundle with no nostr.

## Who needs it

- **seed-firmware (A10.37),** whose source changes from `firmware/active/` to a published release.
- **import nostr (A10.32), export nostr (A10.34) and copy-node (A10.24),** each of which takes on a firmware case.
- **Whoever starts a new instance,** which would install its firmware from relays rather than from the image's files.
- **Whoever keeps the firmware,** whose changes would stop being pull requests to `firmware/` and become releases.

## Done when

The decider has merged the ADR. It names who signs, whose addresses instances use, how a release is pinned, what stays in the repo, and the stories that follow, with what each changes.

## Not in this task

- **The builds.** Each follow-on story is a task of its own once the ADR is merged. This pull request changes no code and no firmware.
- **The wire format of a release.** If the decision adds a convention that other implementations read, its spec in NosFabrica/protocols is a record task of its own.
- **Moving existing instances' graphs.** The recommended option keeps every instance's addresses as they are, so nothing moves. Either other option would need a migration task of its own.
- **Export's open questions that firmware doesn't need answered:** whether an export carries other people's elements (catalog §10, question 9), references to nodes with no nostr address (design doc §5, question 4), and who may sign as the assistant (catalog §10, question 2). They stay with A10.34.
