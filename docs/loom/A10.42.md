# A10.42 Decide how markdown in a Tapestry graph links to another node: nostr:naddr for a node with an address, tapestry:<tapestryKey> for any node

A decision task under Loom's A10 (Graph operations), drafted from proposal P-159. This is its plan. The decision is ADR [graph-rules/0002](../../engineering-team/decisions/graph-rules/0002-markdown-links-to-nodes.md), in the same pull request. Its decider accepts it by merging it.

## The question

Markdown that a Tapestry graph holds needs a way to link to another node. Glossary entries' definitions come first: the concept "tapestry glossary entry" on david.tapestry.ninja has a `definition` field, a string its JSON Schema calls markdown, and its entries name each other's terms.

The link has to keep working when the target is renamed or given an alias, so a link by the term's name, such as `[[concept header]]`, won't do. It also has to work for nodes that exist only in the graph, since many nodes have no nostr event and none should be published just so it can be linked to. P-159 proposes two link forms: `nostr:naddr…` (NIP-21) for a node with a nostr address, and `tapestry:<tapestryKey>` for any node. Export nostr rewrites the second into the first when it publishes.

## What the decision settles

1. The two link forms, and what each names.
2. That a `tapestry:` link means "in this graph": keys are random on each instance (BIBLE §29), so on another instance the link is dead, never wrong.
3. What export nostr (A10.34) does with a `tapestry:` link: rewrites it to `nostr:naddr…` when the target has a letter, and otherwise drops the link, keeps its text and reports it.
4. That renderers resolve both forms with `graph resolve`.
5. How `tapestry:` differs from BIBLE §29's `lmdb:<tapestryKey>`, the pointer that stores a property's whole value.
6. The stories that follow: the rewrite in export nostr, rendering both forms, and a check for links whose target was deleted (A10.31).

The ADR weighs three options: the two forms as proposed, `nostr:naddr` only, and a link by the term's name.

## Who needs it

- **The glossary's writers,** who want to link entries now and need the links to last through renames.
- **Export nostr (A10.34),** which needs to know what to do with each `tapestry:` link before it signs a letter.
- **Whoever builds a markdown renderer.** Tapestry's UI has none yet; `ui/src/components/NoteContent.jsx` only turns `nostr:` entities in notes into links.
- **`rules check` (A10.31),** which can report links whose target is gone.

## Done when

The decider has merged the ADR. It names the stories that follow, what each changes, and whether a firmware reinstall is needed.

## Not in this task

- **The builds.** Each follow-on story is a task of its own once the ADR is merged. This pull request changes no code and no firmware.
- **References in tags,** and whether export adds unpublished nodes to its scope or stops (design §5, question 4; A10.34).
- **Links to people** (`nostr:npub…`, `nostr:nprofile…`), which keep NIP-21's meaning.
- **Editing glossary entries.** No instance writes.
