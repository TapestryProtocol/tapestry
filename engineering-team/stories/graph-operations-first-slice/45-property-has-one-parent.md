# Story 45: a property hangs under one parent — `rules check` finds a property hung twice, `rules repair` takes off the extra link to its JSON schema, and the old routes stop making them

**Status:** Approved
**Created:** 2026-11-19
**Type:** Bug
**Loom:** A10.31.a — https://loom.brainstorm.world/t/A10.31.a

## Background

Grok pointed out to the owner that, on david.tapestry.ninja, a property node is wired straight to a JSON schema node. BIBLE §6 says a property hangs, by `IS_A_PROPERTY_OF`, under the concept's primary property (top level) or under its parent property (nested), and only the primary property's own link goes to the JSON schema ("Top-level schema properties wire to the **Primary Property** (not directly to the JSON Schema)"). The owner asked for it to be found and fixed, then chose to fix it in code first: one rule, its check and its repair, the first piece of Loom A10.31, plus two cheap fixes to the old routes that make such properties (2026-11-19, "Yes, that scope").

Loom's A10.31.a asks for it. Done, for Loom, is when "the rule is declared once, check and repair answer at `/api/tapestry/rules/<operation>` for the owner and admins with their internal CLI commands and /docs entries made from the declaration, there is a test for each thing they refuse or report, the two routes are fixed, and an agent has repaired grok bot through the external CLI." A10.31, its parent, asks for all of `rules list-rules`, `check` and `repair` over every rule (catalog §4, Rules); this story is its first piece, and A10.31 stays open after it.

Eight facts shape the story:

- **The case.** On david.tapestry.ninja, grok bot's property `project` (tapestryKey `7675c11c-e9ee-4310-9c44-b5c8824ea5cb`) hangs under both the concept's primary property (`7a16470e-7cc5-4174-b5a8-1bca81f0162f`) and its JSON schema node (`8a31de59-06af-4abb-aaad-aa69b0b5b6a7`). Grok Bot, an admin agent, made the property with `graph add-property` on 2026-11-18 at 23:21 UTC, under the primary property alone: its change entries say so, and its address, `project-932f40da`, hashes the primary property's address, as BIBLE §6's address rule asks. The extra link came afterwards, when Grok Bot linked the property to the projects concept with the old route `POST /api/normalize/enumerate`, which also signed a relationship element for that link (`55641f3d-db36-4359-98d3-cd7528cec4d8`, "project IS_A_PROPERTY_OF JSON schema for the concept of grok bots") and published it to the instance's relay. A read of the whole graph through the instance's public read route (2026-11-19) found 175 property nodes: 174 under one parent, and `project` under two. Ledger row `2026-11-19-old-routes-hang-properties-on-schema` records the case.
- **Why the old route does it.** `POST /api/normalize/enumerate` was written on 2026-03-07, when the BIBLE's table said `IS_A_PROPERTY_OF | Property → JSONSchema`: every property hung on the schema, and a property "already wired" to the schema was already in the tree. On 2026-03-11 the model changed, the primary property became the tree's root, and the property writes and the BIBLE followed, but the route did not. So it finds no link to the schema on a property built the new way, and adds one every time. When it is asked to make the property (`createProperty`), it makes one whose only parent is the schema link, with an address taken from the `property` concept rather than from a parent.
- **The old create-property route does the same.** `POST /api/normalize/create-property` hangs a top-level property, one given no parent, on the concept's JSON schema node. It takes every property's address from the `property` concept, not from its parent, so the same name created under two parents, on two concepts or in one, is one node with two parents. That happens even when the parent given is the primary property, as a concept's New Property form gives it by default. The rulebook already notes that such a node, off the schema node, is one "concepts can share" (rule 3, `field-mark-allowed`).
- **A tangled tree stops every property write on its concept.** `graph add-property`, `update-property`, `remove-property`, `set-schema`, `enumerate` and `unenumerate` refuse a concept whose property tree has a node under more than one parent (`tangled-tree`, ADR graph-operations-first-slice/0018), and change nothing. So none of grok bot's properties can be changed through them now.
- **Nothing can take the extra link off today.** `graph remove-relationship` refuses `IS_A_PROPERTY_OF`, which only `graph add-property` makes (`reserved-type`, rule 2, `relationship-type-allowed`); the one operation that takes a property's link out, `remove-property`, takes out the whole property and refuses the tangled tree first; and write Cypher is the owner's alone. The ledger row names the way: `rules check` reports a property node with more than one parent, and `rules repair` removes the extra link to the JSON schema, keeping the primary property's own.
- **How a rule is built.** Each rule is defined once, as one `violations` in its own file, and used two ways: as a guard in each write that could break it, and in `rules check`, with repair (design D3; `docs/GRAPH_RULES.md`). The rulebook holds ten entries; several already say "`rules check` (A10.31) will run it over the graph". Firmware installs each entry as an element of the graph rule concept, made from the rulebook and the rule's code, so a new entry reaches an instance's graph at its next firmware install.
- **The old tools get only cheap fixes.** The owner's D15 (2026-11-08): "we shouldn't spend an inordinate amount of effort bringing the old tools up to code if our eventual plan is simply to deprecate them. If there's low hanging fruit, then OK". Stopping the two routes from hanging properties on the schema, and giving create-property's nodes their parent's address, are that kind of fix; the other places the ledger row names stay as they are (out of scope).
- **The write path and the CLI are built.** A10.4 gives a write its guards, one transaction with its change entry, and no signing (ADR graph-operations-foundation/0004). The external CLI (A10.6) turns each operation the instance lists into a command, so `rules check` and `rules repair` reach agents with no change to it.

## User-facing description

As an admin agent or the owner, I want to ask which properties hang under more than one parent, in the whole graph, in one concept or for one node, and be told each one with its parents, so that I can see why a concept's property writes are refused.

As the same agent, I want one call to take off a property's extra link to its concept's own JSON schema, keeping its place in the tree and recording the change, so that the concept's property writes work again with no raw Cypher; and I want to be told, rather than have it guessed, when a property's parents need a choice only I can make.

As the owner, I want today's enumerate and create-property routes to stop hanging properties on the JSON schema, so that the next agent who uses them doesn't make the same tangle.

## Acceptance criteria

- [ ] **AC1 — The rule.** The rulebook gains one entry, `property-has-one-parent`, in its format: every property node hangs, by `IS_A_PROPERTY_OF`, under exactly one node; a concept's primary property under its own concept's JSON schema node, and every other property under a property, its concept's primary property at the top level or its parent property when nested (open question 3 for a property under none). It only reports: it refuses no write. Its code is its one definition, used by the check (AC2) and the repair (AC3), and the property writes still refuse a tangled tree as they do today. Its graph rule item is made from the entry and the code, as every rule's is, and reaches each instance at its next firmware install; check and repair need no install.
- [ ] **AC2 — `rules check` reports it.** Given the owner or an admin is signed in, when they call `GET /api/tapestry/rules/check` with a scope (the whole graph, one concept by its header's tapestryKey, or one node by its tapestryKey) and, optionally, the rules to run, then the answer names the rules it ran and every violation found: the rule, the property node (its tapestryKey, name and address), the concept or concepts whose tree it is in, each of its parents (tapestryKey, name and what it is: the concept's primary property, another property, its own concept's JSON schema, another concept's JSON schema, or another kind of node), and the repair that fixes it, or that none does and why (AC4). It judges every property node in the scope, whoever made it. A scope with none answers an empty list. Nothing changes and no entry is recorded. On a graph like david.tapestry.ninja's, a check of the whole graph names grok bot's `project`, under the primary property and the JSON schema, and nothing else.
- [ ] **AC3 — `rules repair` takes off the extra link to the schema.** Given a violation whose property hangs under one parent in its concept's tree and also directly under that same concept's JSON schema node, in one of the instance's own concepts, or in a firmware concept with the firmware override given (open question 2), when the owner or an admin calls `POST /api/tapestry/rules/repair` with that violation, or with the rule and a scope that holds it, then, in one write, the `IS_A_PROPERTY_OF` from the property to the JSON schema node is gone and the link to its tree parent stays. The property's address, tapestryKey, tags, JSON, its `ENUMERATES` and its membership in the `property` concept stay as they were, and the concept's JSON schema reads back as before. The answer gives each fix made and the change entry, which `graph history` finds by the property, the schema node and the concept. Nothing is signed or sent to a relay. Afterwards a check of the concept reports nothing for the property, and the concept's property writes (`graph update-property`, for one) are no longer refused `tangled-tree`. A repeat changes nothing, records nothing, and answers that there was nothing to repair.
- [ ] **AC4 — The choices left to you.** Every other violation is reported by the repair as a choice left to the caller, with nothing changed for it: a property under two properties, or under two concepts' trees, as create-property's shared nodes are; a property whose only parent is a JSON schema node, or another kind of node; a primary property under anything but its own concept's schema; and any violation in another author's concept (open question 2). The answer says what each parent is and how to go on, naming the operation where there is one. A repair over a scope fixes what AC3 fixes and reports the rest, in one answer.
- [ ] **AC5 — What they refuse.** Check and repair each refuse, change nothing, record no entry, and say in words what was wrong, naming the input: a scope that names no node; a rule the rulebook doesn't hold; a rule the check can't run yet (open question 1), naming A10.31; a violation that doesn't match the graph as it is now, for repair; and, for repair, a violation in a firmware concept without the firmware override (open question 2): the refusal names the override. A repair over a scope fixes what it may and lists each firmware violation it left for want of the override, in one answer. Codes and statuses are Architecture's.
- [ ] **AC6 — The old enumerate route stops hanging properties on the schema.** Given a property under its concept's primary property, when `POST /api/normalize/enumerate` links it to a source concept, then it makes the `ENUMERATES` and signs its relationship event as today, and adds no `IS_A_PROPERTY_OF` to any JSON schema node and signs no event for one; afterwards the concept's property writes are not refused `tangled-tree`. When the route makes the property (`createProperty`), the new node hangs under the target concept's primary property, takes its address from that parent as BIBLE §6's address rule asks, and never hangs on a schema node. Its other behavior stays as it is (D15).
- [ ] **AC7 — The old create-property route does the same.** `POST /api/normalize/create-property` hangs a property given no parent under the concept's primary property, never its JSON schema node, and refuses a concept with no primary property, saying how to go on. Every property it makes takes its address from its parent, so the same name made under two parents is two nodes, each under one parent, and a check (AC2) reports neither. Its other behavior stays as it is (D15).
- [ ] **AC8 — It lasts, and it reaches agents.** After a backup restored on a fresh instance, a repaired property stays under its tree parent alone (BIBLE §30), and after a firmware reinstall the removed link has not come back. The two operations are for the owner and admins: a caller who isn't signed in is refused with 401, and a signed-in person who is neither with 403. They are listed for agents and have their `/docs` entries, made from their declarations. Someone with a shell inside the instance runs `tapestry rules check` and `tapestry rules repair` with no sign-in and gets the routes' answers, and the repair's entry names the command as who made it. On a scratch stack, an admin agent with its own key, through the external CLI and with no change to it, checks a concept whose property hangs under both its primary property and its JSON schema node and is told so, repairs it, checks again and is told nothing is wrong, changes the concept's property with `graph update-property`, and repeats the repair and is told there was nothing to repair. Once the change reaches david.tapestry.ninja, and on the owner's yes, Zeus does the same for grok bot's `project` and deletes the route's relationship element with `graph delete-node`.

Eight criteria in two parts: the rule with its check and repair (AC1–AC5, AC8), and the two old routes (AC6–AC7). They stay one story because they are one Loom task, one fix to one bug, and one reviewable change; split, the routes would be story 46, with its own gates.

## Concepts touched

The handles use this instance's assistant pubkey (`GET /api/assistant/pubkey`); it differs on every instance, so it is never written into code.

- Any concept, through its header, its JSON schema node, its primary property and its property tree (read; the repair writes one link).
- `39998:<TA>:property` — property (read): its elements are the property nodes the rule judges.
- `39998:<TA>:primary-property` and `39998:<TA>:json-schema` — primary property and JSON schema (read): the two kinds of node a property's parent is judged against.
- `39998:<TA>:graph-rule` — graph rule (firmware): gains one item for the new entry, at the next install.
- `39998:<TA>:relationship` — relationship (read): holds the relationship element the old enumerate route signs; this story deletes none, and Zeus deletes grok bot's with `graph delete-node` (AC8).
- On david.tapestry.ninja: the grok bot concept and its `project` property, and the projects concept, its source.

## Out of scope

- **The rest of A10.31:** `rules list-rules`, and running the other rules in `rules check` and `rules repair` (open question 1).
- **A guard for the rule** in the writes: no new write can break it, and the property writes already refuse a tangled tree.
- **The other places the ledger row names:** `generate-property-tree`'s fallback to the schema for a concept with no primary property; the readers that expect a property's parent to be the schema (the property counts on the Concepts pages, the "(top level)" label, the audit's wiring rule, the reading views); and firmware's `property-membership.json`, which still says `nodeToType: "jsonSchema"`. They stay on the row.
- **The old enumerate route's other ways:** it finds the property and both concepts by name, the first match anywhere in the graph; it stays so (D15). `graph enumerate` (A10.19) is the way that doesn't.
- **Retracting the route's relationship letters** from relays (`export retract`, A10.34), and deleting relationship elements in the repair.
- **Moving a property hung only on a schema node into its concept's tree,** and choosing between two trees for a shared node (AC4): the repair reports them.
- **Running a firmware install** for the new graph rule item, which waits for the owner, as rule 9's did.
- **Checking the other instances.** The check makes it one call on each; running it there, and repairing what it finds, wait for the owner's yes.
- Merging to staging and shipping to production, which wait for the owner's OK (the book's frame).

## Open questions

Resolved at this gate. Each carried the drafting's proposal; the owner approved the story with questions 1 and 3 as proposed, and changed question 2 (2026-11-20).

1. **Which rules does `rules check` run in this story?** *Resolved: this rule alone (the drafting's proposal, approved by the owner, 2026-11-20). Asked for another rule, check refuses, naming it as one A10.31 will run, so the answer never suggests the graph was checked for what it wasn't.* The other choice is to run every rule whose `violations` already takes a node or a set, over the graph, now: rules 5 to 8 say they will be run so, but each needs its own way to list what to judge across the graph, and its own tests, which is A10.31's work.
2. **Whose concepts may `rules repair` change?** *Resolved: the instance's own, and firmware's too, but only with a firmware override the caller gives; without it, a firmware violation's repair is refused. Another author's concept is reported as a choice left to the caller* (the owner's change to the drafting's proposal, 2026-11-20: "let's allow it to change even firmware's, but it should require something like a firmware-override flag. Without the override, the change is denied"). AC3, AC4, AC5. The drafting had proposed leaving firmware's concepts out, as the property writes do (`firmware-concept`), since firmware's trees are firmware's definition. `IS_A_PROPERTY_OF` is in no tag today, so the link is the graph's own on any node; a peer's tree stays their claim (D4).
3. **Is a property under no parent a violation?** *Resolved: not in this story (the drafting's proposal, approved by the owner, 2026-11-20). The rule judges properties that hang under something: under more than one node, or under the wrong kind.* `generate-property-tree` unhooks the properties a new schema drops, on purpose, so other instances may hold many such nodes, and nothing in this story repairs them. david.tapestry.ninja holds none (2026-11-19). The other choice is "exactly one" in full, which reports each unhooked node.

For Architecture, not this gate:

- **The rule's name and its words,** and how it lists the property nodes in a scope: by label, through the `property` concept, or through each concept's tree.
- **What a violation is,** as check gives it and repair takes it, so that a repair can tell when the graph has changed since the check (AC5).
- **The firmware override:** its name and form, what the answer and the change entry say when it was used, and whether a firmware reinstall puts back a link it took off.
- **Which lock the repair takes,** so that it and a property write on the same concept go one after the other.
- **Whether a reinstall or an import makes the link again** from the route's relationship element, which stays in the graph and on the relay (AC8).
- **The two old routes:** how create-property finds the primary property, and what its new address means for a name it made before under the old address.
- **The answers' and the change entry's shapes,** and the refusals' codes and statuses.
