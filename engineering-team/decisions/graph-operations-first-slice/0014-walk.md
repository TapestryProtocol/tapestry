# ADR 0014: `graph walk` — a walk taken one step at a time, each node reached once on a shortest path, nearest first, within a bound on the relationships it reads, in one engine search can call

**Status:** Accepted
**Date:** 2026-11-16
**Story:** `engineering-team/stories/graph-operations-first-slice/14-walk.md`

## Context

The story (Loom A10.14) asks for one graph read, written so that `graph search` (A10.8) can call it. Its criteria, in short:

- **AC1** — `GET /api/tapestry/graph/walk` with `from` (one or more tapestryKeys) answers every node the walk reaches within `depth` steps, each once. `types` names the relationship types it steps along, declared or not, and every type when left out. `direction` is `out`, `in` or `both`, the default. The answer gives the start nodes with their five facts, and the types, direction, depth and point of view it walked by.
- **AC2** — each node comes with its five facts, how many steps it is from the nearest start node, and the path that reached it: the start node, then each step as a relationship as C5 answers one, read from the node the step leaves. The path is a shortest one, the same one each time the graph is the same. A walk never steps onto a node it has already reached. A start node is never answered as reached.
- **AC3** — with no `types`, the walk doesn't step onto tag nodes, and the answer says how many it didn't step onto. With `types`, it steps wherever they lead.
- **AC4** — the owner's point of view by default. A walk steps only to a node that counts by C2's test, and reaches nothing by way of a node that doesn't. The start nodes are never left out. The answer counts the nodes reached and those left out across the whole walk, and says when the owner's scores don't exist yet. `pov=everyone` steps onto every node. Nothing is stored. Any other `pov` is refused.
- **AC5** — pages of at most `limit` (1–200, 50 by default), nearest first: by steps, then by tapestryKey, with a cursor that is null on the last page. Paging answers every node exactly once while the graph doesn't change. A walk stops at a bound, answers every step it finished within it, and says it stopped short and how many steps it finished. A cursor this read didn't give, for the same inputs, is refused, and so are a `depth` or `limit` out of range.
- **AC6** — refusals: no `from`, or one that names no node (a change entry is not one), saying which; a malformed `from`, too many start nodes, a malformed `types` entry or `direction`; an input the read doesn't take.
- **AC7** — it writes nothing; 401 and 403 for everyone but the owner and admins; listed for agents, in `/docs`, and run by `tapestry graph walk`; an admin agent uses it through the external CLI on a scratch stack. The walk is defined once, so `graph search` can call it from code and get the same answer. Today's subgraph route keeps answering as it does.

The owner settled the story's questions at its gate (2026-11-16):
1. Each node comes with one shortest path, given whole.
2. Nearest first, by steps and then tapestryKey, paged with `limit` and a cursor. A change between pages that alters a node's distance can move that node.
3. `depth` runs from 1 to 10, 1 by default, and up to 100 start nodes. A walk stops at a bound, set here from the live check's timings, answers every step it finished, and says it stopped short.
4. `direction` is `both` by default, as list-relationships takes it. With no `types`, tag nodes are left out and counted (ADR 0013's reasons hold for walk).

## Options considered

### Option A — A walk taken one step at a time, in a shared engine (chosen)

A new module, `src/operations/walk.js`, beside `reads.js` and `resolve.js`, walks. For each step it runs one directed statement per direction asked for:
- from every node the walk is at (the frontier);
- to nodes it hasn't met yet, which a parameter lists.

JavaScript keeps the walk's books: the nodes met, each new node's parent and the relationship that reached it, the counts, and the bound. `graph walk`'s declaration, `src/operations/catalog/graph/walk.js`, pages the result. Search calls the engine.

- **Pros:**
  - Plain Cypher of the shapes list-relationships already runs. Each step's direction comes from its statement, as ADR 0013 Option A has it.
  - A step reached only from the frontier gives shortest paths: every node is met first at its least distance.
  - Leaving out the nodes met inside the statement means a walk never steps onto a node twice. A cycle, a relationship walked back and a relationship from a node to itself end there.
  - Which of several shortest paths is chosen is a rule in JavaScript, the same each time the graph is the same (AC2).
  - Each statement's `LIMIT` caps what it reads, so the bound holds step by step.
  - The fakes need one more route, for a step anchored by a list, and nothing new in the path fake's Cypher.
  - Search gets the same walk by calling a function (AC7).
- **Cons:**
  - Up to two statements a step, so up to 22 a page at depth 10 with `both`, beside the scores and the start nodes.
  - Each page reads the whole walk again: the counts are across the whole walk (C2), and nothing is stored.
  - The list of nodes met, up to the bound's size, goes to every step's statement as a parameter.

### Option B — One statement per page, with Neo4j's shortest-path search

`MATCH p = ANY SHORTEST (s)-[:T1|T2]-{1,10}(m)`, with a quantified path pattern (Neo4j 5.21 and later), answers one shortest path to each node reached from each start. GDS's breadth-first search, over a projected graph, is a variant.

- **Pros:** one statement per page, and Neo4j does the search.
- **Cons:**
  - Which of several shortest paths comes back is Neo4j's choice. Nothing promises it is the same each time (AC2).
  - The point of view must hold at every node along a path. The trust test would have to run inside the quantified pattern, a `NostrUser` lookup at each node.
  - It can't stop at a bound partway: a `LIMIT` after `ORDER BY length(p)` waits for the whole search. A variable-length match without `SHORTEST` lists every path, which grows past any bound through a busy node.
  - The fakes run no path variables, quantified patterns or `SHORTEST`, so they would need a new interpreter. GDS needs a graph projected for each walk.

### Option C — Keep each walk, and page from the kept copy

The first page walks and keeps the result, in Redis say, under the cursor, and later pages read it.

- **Pro:** one walk per walk, not per page.
- **Con:** it stores a point of view's view of the graph, which principle 3 forbids. A score change or a write after the first page would never reach the later pages. A cursor would then depend on what the server kept, which a restart loses.

**Smaller choices inside Option A, with what was turned down:**

- **The bound counts the relationships a walk reads, not the nodes it reaches.** A step's rows, one for each relationship to a node not yet met, are what the step costs, and a walk reaches at most as many nodes as it reads relationships. So it never answers more nodes than the bound, though several relationships to one node can make it stop a little sooner.
  - Turned down: counting distinct nodes exactly in Cypher. The aggregation is eager, so a `LIMIT` after it caps nothing read.
- **The bound is 10,000 relationships for each walk.** That is the dense hub list-relationships paged through at 67 ms a page at the median (story 13's Evidence). It is about the 8,000 typed links of Avi's brain, and four times the local graph's busiest node.
  - Relationships to tag nodes count against it, since reading them is part of a step's cost: one step from 40 headers read 279 of its 324 that way (Context 10). A typed walk reads none.
  - The live check times a page of a walk that reads that many, with types and without. If a page is too slow, the Implementer lowers the bound; if pages at the bound are quick and walks with no types stop short too soon, the Implementer raises it. Either way the story's Deviations record why, as its question 3 asks.
- **The tie-break.** Among the relationships that reach a new node at one step, out before in, then the least tapestryKey of the node it came from, then type, then `elementId`. The direction comes first because the outgoing statement runs first, and the incoming one leaves out what it met.
  - Turned down: whichever row Neo4j returns first, which isn't promised to be the same.
  - Turned down: comparing whole paths key by key, which costs more and gains nothing a caller can see.
- **The nodes met are left out inside the statement** (`$known`), not in JavaScript.
  - Turned down: returning them and dropping them in JavaScript. Under `both`, every node's relationship back to its parent would come back and count against the bound.
- **A node left out, or a tag node passed by, is met:** counted once, never read again, and never a step.
- **Paths are built only for the page's nodes,** by following each node's parent back to its start node.
- **The whole walk for each page.** The story's counts are across the whole walk, and nothing is stored, so every page walks again, capped by the bound.
  - Turned down: walking only as far as the page needs, which would leave the counts unknown.

## Decision

We chose **Option A**. It is the only option that gives one shortest path per node, the same each time, without leaning on an engine's choice. It can stop at a bound one step at a time, and the fakes can run it. It puts the walk in one function, which search calls as the read does (AC7). Its cost is the whole walk on every page, which the bound caps and the live check measures.

### 1. The engine, `src/operations/walk.js`

A shared module beside `reads.js` and `resolve.js`. Like them, it opens nothing at load. It exports:

| Name | What |
|---|---|
| `FROM_INPUT`, `TYPES_INPUT`, `DIRECTION_INPUT`, `DEPTH_INPUT` | the inputs' declarations (Decision 2), so search can take the same ones |
| `MAX_FROM` 100, `MAX_TYPES` 50, `MAX_DEPTH` 10, `BOUND` 10,000 | the limits |
| `REACHED` | the schema of a node reached (below) |
| `UNKNOWN_NODE` | `{ code: 'unknown-node', status: 404, when }` |
| `walk(read, options)` | the walk |

**`walk(read, { from, types, direction, depth, pov, bound = BOUND, input = 'from' })`.**
- `read` is `(cypher, params) → rows`: `graph.read`, or a write's `tx.read`.
- `pov` is a resolved point of view (C2).
- `types` is null or a list.
- It throws an `Error`, never a refusal, for a call no operation's schema would let through, as `trust` does: `from` not a list of 1 to `MAX_FROM` tapestryKeys, a type that fails `TYPE_PATTERN`, a `direction` other than `out`, `in` or `both`, a `depth` that isn't a whole number from 1 to `MAX_DEPTH`, or a `bound` below 1.

It returns:

```js
{
  from: [NODE, …],                // the start nodes, in the order given, each once (C3)
  reached: [{ tapestryKey, name, address, author, own, depth, start }, …],   // nearest first: depth, then tapestryKey
  kept: 120,                      // how many nodes it reached (reached.length)
  leftOut: 3,                     // nodes it didn't step onto because the point of view doesn't count them
  tagsLeftOut: 40,                // tag nodes it didn't step onto because no types were given; 0 with types
  complete: true,                 // false when it stopped short at the bound
  finished: 2,                    // the steps it finished: depth when complete
  pathOf(tapestryKey) → [RELATIONSHIP, …],   // a reached node's path, its first step from its start node
}
```

The counts cover the steps it finished. `depth` is how many steps the node is from the nearest start node, and `start` is the tapestryKey of the start node its path sets out from.

**What it reads.** Every statement goes through `read`, and none writes.

- **S1, the start nodes.** No relationship, so `nodeCypherFake.js` runs it:

  ```cypher
  MATCH (n:TapestryNode)
  WHERE n.tapestryKey IN $starts AND NOT n:GraphChange
  RETURN <nodeColumns(n)>
  ```

  A key with no row refuses `unknown-node`, `input` as given, and the message names each such key. The start nodes are answered whatever their author: the caller named them (C6).
- **S2, one step in one direction.** Outgoing:

  ```cypher
  MATCH (x:TapestryNode)-[r]->(m)
  WHERE x.tapestryKey IN $frontier
    AND NOT m:GraphChange AND m.tapestryKey IS NOT NULL AND m.tapestryKey <> '{}'
    AND NOT m.tapestryKey IN $known
  WITH x, r, m, (NOT $tags AND m:NostrEventTag) AS hidden
  <trust('m', ['x', 'r', 'hidden'])>
  RETURN x.tapestryKey AS parent, <relationshipColumns(r, m)>, hidden, counts
  LIMIT <n>
  ```

  - **Incoming** is the same with `MATCH (x:TapestryNode)<-[r]-(m)`.
  - **With `types`,** the relationship is `[r:\`A\`|\`B\`]`: each type checked by `TYPE_PATTERN`, each once, sorted, in backticks. The direction and the types choose the text, and nothing else from input does.
  - **`$frontier`** holds the tapestryKeys of the nodes the walk is at: the start nodes for step 1, then the nodes the last step reached.
  - **`$known`** holds every node met so far: the start nodes, the nodes reached, those left out, and the tag nodes passed by.
  - **`$tags`** is true when `types` are given, so `hidden` is then always false.
  - **`<n>`** is the bound less the relationships read so far, plus one: a checked whole number written into the text (C1).
  - The filter is list-relationships' F, so a node with no tapestryKey, or with `'{}'`, is neither met nor counted. A change entry never is.

**The steps.** For step 1 to `depth`, while the frontier isn't empty:
1. **Read.** Run S2 for each direction asked for, out before in. The incoming statement's `$known` includes what the outgoing one met at this step.
2. **Sort each row.**
   - With `hidden`, it is a tag node passed by.
   - Without `counts`, it is a node left out.
   - Otherwise it reaches a new node. Of the rows that reach one node, the step keeps the least by the tie-break: out before in, then `parent`, then `type`, then `rid`.
3. **Check the bound.** If this step's rows would take the walk past the bound, which a statement shows by returning `<n>` rows, the step is dropped whole. Its nodes are neither answered nor counted, `complete` is false, `finished` is the step before, and the walk ends.
4. **Keep the step.** Its new nodes become the frontier, at `depth` = the step. Each keeps its parent, its direction and its row: its step is `relationshipOf(row, { key: parent, direction, own: pov.own })`. Everything it met joins `$known`.

The walk ends complete when it has finished `depth` steps, or when a step reaches nothing new. `finished` is then `depth`.

**What a node reached is answered with, `REACHED`.** C3's five facts, then:
- `depth`: whole number, 1 or more;
- `start`: the tapestryKey of the start node its path sets out from;
- `path`: a list of C5 relationships, in order. The first leaves `start`, each later one leaves the node the step before reached, and the last reaches this node. Each relationship is read from the node it leaves: its `direction` is `out` when it runs from that node, and its `node` is the node it reaches.

As C3 and C5 allow, these are facts beside the five, and none is renamed or dropped.

### 2. `graph walk`, `src/operations/catalog/graph/walk.js`

A read, `owner-and-admins`, declared with `run`.

**Inputs.**

| Input | Schema | Notes |
|---|---|---|
| `from` | `{ type: 'array', items: { type: 'string', pattern: N.KEY_PATTERN }, minItems: 1, maxItems: 100 }`, required | the start nodes' tapestryKeys, one value for each (`from=<key>&from=<key>`, `--from <key> --from <key>`) |
| `types` | `{ type: 'array', items: { type: 'string', pattern: N.TYPE_PATTERN }, minItems: 1, maxItems: 50 }` | the types to step along, declared or not; every type when left out |
| `direction` | `{ type: 'string', enum: ['out', 'in', 'both'], default: 'both' }` | for the whole walk |
| `depth` | `{ type: 'integer', minimum: 1, maximum: 10, default: 1 }` | how many steps at most |
| `pov` | `R.POV_INPUT` | `owner` by default |
| `limit` | `R.LIMIT_INPUT` | |
| `cursor` | `R.CURSOR_INPUT` | |

`from`, `types`, `direction` and `depth` take `walk.js`'s declarations, which carry their descriptions.

**Refusals** (its own, beside the built-in `missing-input`, `invalid-input` and `unknown-input`):

| Code | Status | When |
|---|---|---|
| `unknown-node` | 404 | a `from` that names no node of the graph (a change entry is not one); `input: 'from'`, and the message names each such key |
| `unknown-pov` | 400 | from C2 |
| `invalid-cursor` | 400 | from C1 |

Too many start nodes or types, a malformed key, type or direction, and a `depth` or `limit` out of range are `invalid-input`, from the schemas, each naming its input.

**`run`, in order:**
1. Check `limit` and `depth` again, as list-elements checks `limit`.
2. Take `from` each once, in the order given, and `types` each once, sorted, or null. `direction` is `both` when left out.
3. Resolve the point of view (C2), which may refuse `unknown-pov`.
4. Work out the scope from `[from, sorted; types; direction; depth; pov.name]`, then decode the cursor if there is one.
   - Its position is `[depth, tapestryKey]`, the last node of a page. It passes only when the first is a whole number from 1 to `depth` and the second matches `KEY_PATTERN`. Anything else is refused `invalid-cursor`.
   - The scope takes `from` sorted because the walk doesn't depend on the order it was given in.
5. Call `walk(read, { from, types, direction, depth, pov })`. Its S1 may refuse `unknown-node`.
6. Page the reached nodes after the cursor's position, those with a greater depth or the same depth and a greater tapestryKey, with `pageOf(rest, limit, (last) => encodeCursor(READ, scope, [last.depth, last.tapestryKey]))`.
7. Answer, building each page node's `path` with `pathOf`.

**The answer:**

```js
{
  from: [NODE, …],                  // the start nodes, in the order given, each once
  types: ['HAS_ELEMENT', …] | null, direction: 'both', depth: 2,
  pov: { name: 'owner', observer: '<hex>', cutoff: 0.05, scored: true },
  kept: 120, leftOut: 3, tagsLeftOut: 40,   // across the whole walk (the steps it finished)
  complete: true, finished: 2,
  nodes: [ REACHED, … ],            // this page, nearest first
  cursor: '<text>' | null,
}
```

The cursor holds no relationship type, so ledger row `2026-11-16-relationship-cursor-type-narrower` (list-relationships' cursor refuses a type outside `TYPE_PATTERN`) doesn't arise here, though a walk with no `types` can follow such a type. Its paths answer the type as text, as C5 does. The row stays list-relationships' to settle, with its amendment to ADR 0013, since walk doesn't page relationships.

**What it doesn't do:** it answers no relationship that lies on no node's path, takes one direction for the whole walk, and changes nothing.

### 3. How search calls the walk

`graph search` (A10.8) is a read in the same group, so it requires `src/operations/walk.js` as list-relationships requires `reads.js`:

```js
const W = require('../../walk');
const pov = await R.resolvePov(read, inputs.pov);
const walked = await W.walk(read, { from: headerKeys.slice(0, W.MAX_FROM), types, direction, depth, pov, bound });
// walked.reached: every node reached, nearest first; walked.pathOf(key) for the ones search answers
```

- Search's first step, matching concept headers by keyword, gives the start nodes. Its own story picks the types, direction and depth for each strategy (design doc §5, question 7).
- It may pass a smaller `bound` to keep its own pages quick.
- It reads `complete` to say when a walk stopped short.
- It ranks and pages its own answer. It never stores a walk, so its results move with the point of view as walk's do.
- If the first step matches more than `MAX_FROM` headers, which ones it walks from is search's own choice.

### 4. Docs, and the amendment to ADR 0011

- **ADR 0011, Amendment 4,** written with this ADR. C1's rule that an item's place never changes holds for every read but walk. Walk answers nearest first, as its owner chose, and a node's distance depends on the rest of the graph. So a change between two pages that brings a node nearer, or takes it further away, can move it:
  - to a page already read, so it's missed;
  - or to one still to come, so it shows twice.

  Every node whose distance doesn't change is answered exactly once.
- **`src/operations/reads.js`:** C1's paragraph (`:15–22`) names walk's order and that exception, and says walk pages a walk it reads whole rather than fetching `limit + 1` rows. Comment only.
- **`docs/GRAPH_OPERATIONS_CATALOG.md`:**
  - Conventions, Paging: the same, in words.
  - §1's `walk` row: its "What it does" and "Takes → returns" as built.
  - §1's closing paragraph: search calls walk's engine, `src/operations/walk.js`.
- **No rule is added,** so `docs/GRAPH_RULES.md` is unchanged.

## Consequences

**What this enables**
- An agent sees what a node leads to (a concept's sets and elements, the nodes near it), each node once with how it was reached, a page at a time and with no Cypher. It can pass any step of a path straight to `graph remove-relationship`.
- `graph search` (A10.8) builds its second step on the same walk, and inherits the point of view and the bound.
- `graph class-thread-path` (A10.12) can be a walk along the class thread's types, if its own ADR finds that enough.

**What this constrains**
- Every page walks again from the start: up to 22 statements at depth 10 with `both`, and a parameter of up to about 10,100 tapestryKeys to each step. The bound caps it, and the live check measures it.
- A walk stops short at 10,000 relationships read, tag nodes passed by and nodes left out included. A walk from a node with more than 10,000 relationships to nodes it hasn't met answers nothing, and says it stopped before its first step: `graph list-relationships` pages through those.
- A page carries a path for each node, so 200 nodes at depth 10 carry up to 2,000 relationships, each with its node.
- The order is nearest first, with the exception Amendment 4 to ADR 0011 names.
- A cursor is tied to its start nodes, types, direction, depth and point of view.

**Debt and follow-ups**
1. **Provenance.** When relationships record who made them (design doc §5, question 2), C6 widens to judge that too, in `reads.js`. Walk follows with no change of its own.
2. **BIBLE.** §11 gains the read when the book closes (ADR 0011, debt 5).
3. **`$known`'s size.** If the live check finds a long parameter costly, a later change can send a `both` walk only the last two steps' nodes, plus those left out and the tag nodes passed by. In a walk that steps both ways, a node can only meet nodes one step either side of its own.

**Firmware reinstall required?** No: no concept definition changes.

**The live check** runs on a scratch stack (`scripts/scratch-stack.sh`), never on the agent-memory instance:
1. Copy the branch in as list-relationships' check did (its story's Evidence), and link `tapestry`.
2. Run `lifecycle migrate`, so `tapestry_key` is in place, and add `nostrUser_pubkey` as the agent-memory instance has it. Lookups then seek as on a real instance.

Page a walk through it at 50 and at 200, check each node comes once and on a shortest path, and time a page. Then a hub of 12,000 relationships: a walk from it must stop short, and a walk that reads close to 10,000 is timed. If a page there is too slow, lower `BOUND` and record why.
6. Check that the relay's event count and the number of `GraphChange` nodes are unchanged.
7. Do it again as an admin agent with its own key, through the external CLI: `--from` repeated, `--types` repeated.
